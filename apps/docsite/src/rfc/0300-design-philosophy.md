# 0300：AuroraBot 设计思想

状态：现行

日期：2026-08-24

修订：2026-09-13

## 1. 效力与边界

本文件是 AuroraBot 的设计思想，只陈述不可协商的不变量与判断准则。

- 本文件不包含任何实现坐标：不出现包名、模块名、文件名、字段名、类名、协议修订号、命令名、事件名或 ID 规范。
- 实现结构见 `docs/architecture/`，精确词汇见 `docs/reference/`，代码与测试是最终事实。
- 仅当设计思想、语义不变量或边界本身改变时才修订本文件；实现换一种做法而语义不变，不需要改动本文件。
- 当实现与本文件冲突时，以本文件为准；多个实现方案都满足本文件时，取更小、更少状态、更可解释者。
- 源码、测试和配置注释直接说明局部行为与不变量，不引用具体 RFC 编号或章节；历史设计只由 Git 保存。

## 2. 主体与存在方式

- Bot 是主体，不是被调用的接口。她一直存在，拥有自己的人格、状态与边界。
- 她拥有世界与森林：一切影响她的变化先成为世界事实；一次认知运行只是她的一次经历，经历结束她仍然存在。
- 一切输入都有媒介：任何影响她的变化都必须先成为一条世界事实，不得绕过世界直接作用于她。
- 她理解之后才决定：来源不赋予指令权；模型只负责理解与判断，真实行动必须经声明的工具执行，结果再作为新事实回到她的世界。

## 3. 一次运行的最小语义

最小概念集是：运行、节点、消息、模型、工具、世界事实。任何新概念必须证明无法由它们表达。

- 一次运行是唯一聚合根，包含一个根节点与有限节点集合，节点之间只有父子委派关系。
- 节点同构：根与子节点使用同一种节点、消息与循环；实例差异只来自人格提示、初始消息、可见工具与所用模型。
- 节点创建即从被选定的原型复制其提示、模型与工具；原型的后续变化不反向改写已有运行。
- 上下文即状态：模型可见状态只存在于节点的追加式上下文中，不得在旁路状态机复制。
- 模型决定，运行时执行：模型可以回复或请求工具；真实效果只由工具执行，结果再回到上下文。
- 委派就是工具：委派是工具域中的普通可见工具，产生显式的委派请求；运行时不内置委派名称、参数或路由分支。
- 模型选择是节点事实，必须随每次调用显式传递，不得由全局、提供方或提示隐式推导。

运行不变量：

1. 根节点没有父节点，其他节点恰有一个已经存在的父节点；父子关系无环且都从根可达。
2. 深度由父子链推导，不保存为独立事实。
3. 节点上下文以一条消息开始、只追加，且不保存系统消息。
4. 已完成或已失败的节点不得再追加消息或创建子节点。
5. 父节点创建子节点后进入等待；子节点结束后父节点恰好收到一条对应结果并回到就绪。
6. 根节点结束即整次运行结束；非根节点结束不直接结束整次运行。
7. 每个新节点只能由组合时已注册的原型创建；根原型由运行入口显式选择，子原型必须位于父原型的允许集合内。
8. 节点只基于已披露给它的世界事实推理；一个节点观察过的事实不得隐式视为其他节点已观察。

消息角色只有四种：

| 角色 | 含义 |
| --- | --- |
| 系统 | 身份、世界、节点职责与稳定运行约定 |
| 消息 | 来自人、环境或父节点的待理解事实 |
| 助手 | 模型产生的文本与零个或多个工具请求 |
| 工具 | 某个工具请求的一次规范化结果或错误 |

- 领域角色不因来源获得特权；来源到协议的映射只发生在协议边界，且不得泄漏回运行。
- 系统与消息必须有非空文本、不能携带工具请求；助手可以只含文本、只含请求或两者兼有；工具结果必须配对请求、不能再次携带请求。
- 每个请求在节点内唯一，并恰好对应零条或一条后续结果；只有全部未决请求都返回后，节点才能再次请求模型。
- 节点上下文的追加顺序必须始终能重放为合法的模型上下文。

## 4. 世界线

- 世界事实日志是唯一权威、只追加的事实流：环境、输入、运行因果、工具请求与结果、对外发布都进入同一事实流。
- 事实归属由提交方决定；日志只校验、编号与追加，不推断归属，也不产生事实。
- 事实可以归属到若干命名范围，每个范围独立编号；不相关范围的新事实不得互相阻塞。
- 观察以“前沿”表达：前沿是范围到序号的不可变映射，只交付有界索引，正文读取由独立服务承担。
- 披露与行动：模型在行动前必须看到已到达的披露；节点显式选择以当前观察前沿作为行动截面，之后到达的事实与该行动并发，不自动使其饥饿。
- 外部动作与外部事实分属不同归属：外部动作只能经工具执行，外部事实只能追加为世界事实，二者不得互相绕过。
- 运行因果只记录元数据，不复制上下文正文。
- 不确定的外部效果不得自动重试；无法确认效果时必须如实标记为不确定，不得降级为失败或伪装成成功。
- 对外回复必须由 Bot 经可见工具显式完成；运行时不自动投递。
- 诊断是运行观察，不是世界事实：诊断不得进入世界事实、节点上下文或工具结果，也不能替代已有的因果事实。

## 5. 组装与扩展

- 能力自描述：每项能力在自身边界内声明它提供什么、需要什么、贡献什么，以及如何在生命周期各阶段运行。
- 机制与策略分离：组合机制不感知任何具体能力；用哪些能力、如何接线由声明与配置决定。
- 注册变化轴，不注册猜想：只有存在两个真实实现或明确不变量的并列维度才建立注册表；否则不建体系。
- 启动发现，运行冻结：所有会影响运行目录的发现必须在产生运行效果前完成并冻结；运行中目录变化只产生状态与“需重启”，不得热改已有运行。
- 依赖方向单向分层：通用契约与通用工具是最底层叶子；机制层只依赖叶子；能力层运行时不互相引用，跨能力协作只经被注入的契约实例；上层可依赖下层，下层不得反向依赖上层。
- 发现即装配：并列能力由目录约定自动发现并注册；重复、冲突、缺失依赖与依赖环都在产生任何效果前失败，并给出可定位诊断。
- 扩展边界即信任边界：随进程加载的扩展与宿主同权限运行，这是有意的选择，不以隔离为默认。
- 配置是只读项目事实：个人配置与发布模板保持相同拓扑，运行时只读取个人配置，不隐式回退模板，也不把个人修改写回源码；配置形状由能力自身拥有，密钥只来自环境变量。
- 组合机制自身不含任何具体能力名；新增并列能力不应要求修改机制或其他能力。

## 6. 判断准则

遇到设计选择时按以下准则判断：

1. 新概念必须证明无法由最小概念表达，否则不进入核心。
2. 没有两个真实实现或明确不变量时，不建立通用扩展接口或生命周期体系。
3. 任何外部效果都必须可审计、可追溯；任何事实都必须能定位其来源。
4. 不确定效果不得自动重试；只有明确拒绝或可确认无效果才算失败。
5. 隐藏的认知旁路不可接受：任何会触发模型调用、用户询问或独立任务循环的协议能力都必须拒绝或显式失败。
6. 先求可解释，再求可靠：持久化、恢复、并发、授权与运维都必须建立在明确的最小语义之上。
7. 相同语义下选择更小、更少状态、更可解释的方案。
8. 不得用实现便利覆盖上述不变量。

## 7. 非目标

- 平行于“一次运行”的认知运行模型（任务、邮箱、活动、续跑等）。
- 通用事件总线、非单例作用域、运行期热插拔。
- 隐藏的模型调用、用户询问或独立任务循环。
- 运行期目录热替换、自动重连与跨重连效果幂等。
- 远程部署、沙箱、分布式追踪、审计归档与运行期重配置。
- 没有真实用例与不变量的结构配置与测试。

这些方向进入当前实现前，必须先给出围绕最小概念的真实用例、清楚的不变量与独立测试，并先修订本文件。

## 8. 冲突裁决

- 实现与本文件冲突时，以本文件为准。
- 本文件未规定处，实现可自由选择；但一旦该选择影响语义不变量，必须回到本文件判断。
- 本文件与更具体的现行架构说明冲突时，以本文件为准，并修正架构说明。
