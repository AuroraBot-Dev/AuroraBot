# 0303：运行阶段与扩展面

状态：现行（已实施）

日期：2026-09-13

## 1. 动机

组合机制已经能按能力依赖拓扑装配并驱动生命周期，但它的“运行阶段”仍是一组固定的钩子，扩展面仍是封闭的少量公共键，运行前台仍由门面硬编码。结果是：

- 阶段封闭且跨阶段顺序不可表达：只能声明“激活顺序有依赖”，不能声明“某能力就绪后再启动”“运行在另一个后台循环之后开始”“关闭前先排空”。
- 运行流程与具体实现耦合：谁拥有进程前台由门面写死，新前台（服务、守护循环、另一个终端）无法只靠声明接入。
- 扩展面封闭：新增一种“多方追加”的扩展维度必须修改公共契约，机制与策略的边界因此被反复触碰。

本 RFC 规定一套更完整的运行阶段抽象，使运行流程、扩展面与具体实现解耦：每项能力自己声明它在哪些阶段参与、依赖什么才可运行，机制不认识任何具体能力。

## 2. 决策

### 2.1 阶段是一等公民

运行阶段不再是一组固定字段，而是可命名、可排序、可扩展的一等概念。内置阶段至少覆盖：准备、构造、激活、就绪、运行、排空、关闭。能力可以参与任意子集，也可以注册新阶段。

- 阶段之间具有稳定的先后语义：准备先于构造，构造先于激活，激活先于就绪，就绪先于运行，排空先于关闭。
- 同一阶段内，各能力按声明顺序执行。
- 阶段集合的扩展不得破坏上述基本语义。

### 2.2 统一阶段计划

机制把“能力 × 阶段”统一编译成一份有序计划，而不是分别对构造与激活做两次独立排序。阶段按声明的全局顺序分层：构造阶段全部先于运行阶段，运行阶段全部先于关闭阶段。每一阶段内部再按以下边排序：

- 能力依赖：被依赖方在对应阶段的产出先于依赖方；
- 显式顺序约束：能力可以声明“某阶段在某能力完成某阶段之后”，约束以能力（契约身份）而非具体实现名表达；引用更早阶段自动满足，引用更晚阶段是非法声明。

机制对每个阶段做拓扑排序，检测环并给出完整环路。执行顺序完全由声明推导，机制不硬编码任何具体能力。

### 2.3 就绪与排空

区分“已构造”与“已就绪”：构造只产生实例，激活使能力对外可用。依赖方可声明它需要的是就绪而非仅构造。

引入排空阶段：在关闭前给前台与后台循环一个协作停止的机会，使“请求停止”与“释放资源”分离。排空由停止信号触发，必须幂等。

### 2.4 运行前台是贡献

进程前台不再由门面硬编码。引入一个稳定的多值贡献点：每项想拥有进程前台的参与者贡献一个异步“前台”，接收停止信号并在停止前持续运行。

- 协调者只负责：完成装配与激活、并发运行全部已贡献前台、在停止时先排空再关闭。
- 没有前台时，协调者等待停止信号。
- “无界面”只是一种策略：排除交互式前台，而不是门面里的分支。
- 新增前台不得要求修改协调者或机制。

### 2.5 扩展面由提供方声明

扩展点（多方追加的稳定维度）的词汇不再集中维护：

- 提供扩展维度的能力声明并公开该维度的稳定身份；消费方只引用该身份。
- 机制在装配前收集全部被声明的扩展身份，校验唯一性与冲突，缺失或重复即失败。
- 新增一种扩展维度只需新增声明与公开身份，不修改机制，也不修改其他能力。
- 跨包消费的扩展身份必须来自公共契约层；这是类型安全与可发现性的必要共享，不视为耦合。

### 2.6 可审计的阶段计划

机制必须能输出解析后的阶段计划（每项能力在哪些阶段、按什么顺序、依据哪些约束），供人审阅与诊断。启动失败必须指出失败节点、异常与已启动节点列表。

## 3. 必须保住的不变量

- **启动顺序等价**：改造后，由声明得到的执行顺序必须与现行顺序语义等价——世界初始化 → 外部工具发现与贡献冻结 → 工具目录冻结 → 目录交叉校验 → 装配冻结 → 主动节律游标固定 → 外部事件入口激活 → 后台启动。该顺序必须由声明与依赖推导，而不是机制内的硬编码分支。
- **启动发现，运行冻结**：所有影响运行目录的发现仍在产生运行效果前完成并冻结；运行中目录变化只产生状态与“需重启”。
- **先诊断后效果**：重复、冲突、缺失依赖、环、非法阶段与非法约束都在产生任何效果前失败。
- **无平行运行模型**：阶段是进程级的，不为单次认知运行引入第二套生命周期；单次运行仍由认知循环拥有。
- **机制无能力名**：机制与协调者不得按任何具体能力名称增加分支。

## 4. 非目标

- 不引入单次认知运行级别的阶段或生命周期。
- 不做运行期热插拔；装配仍在启动期完成并冻结。
- 不引入通用事件总线、非单例作用域或机制版本协商。
- 不改变最小运行语义、消息角色、模型与工具端口、世界语义。

## 5. 对既有决策的影响

- 扩展 RFC 0302 的生命周期部分：把固定钩子升级为可声明阶段图；能力自描述、能力身份、发现源与配置边界不变。
- 不修改 RFC 0300 的不变量；阶段图只是让既有启动/关闭顺序可声明、可审计。
- 现行实现结构见 `docs/architecture/`，已同步更新。

## 6. 验收标准

- [ ] 新增一个阶段参与者无需修改机制或协调者。
- [ ] 新增一种扩展维度无需修改机制或其他能力。
- [ ] 新增一个进程前台无需修改协调者。
- [ ] 就绪、排空、关闭可分别声明依赖，且关闭顺序由声明推导。
- [ ] 解析后的阶段计划可输出，且非法约束/环在产生效果前失败并给出完整诊断。
- [ ] 由声明推导的启动顺序与第 3 节等价，并有离线测试固化。
- [ ] 机制与协调者中不出现任何具体能力名称。
- [ ] 全量离线测试与质量检查通过。
