# 节律与记忆模型

## 各自决定什么

节律模型为 Bot 分配推理机会，记忆模型为当前问题推荐可选经历。目标、行动和未来安排仍由 Bot 选择；必要检查点和证据不会仅因推荐得分低而被丢弃。两个策略可以分别替换，规则基线也能在相同端口下运行。

GRU 接收环境待处理量、距离上次推理时长、活动目标和待核对行动数量、失败压力、计时到期、即时事件，以及 UTC 日内周期特征；输出思考概率、下一次检查时间和新隐状态。输入计算不需要先运行 LLM，隐状态属于调用方保存的主体循环。

TGN 按获知顺序处理记忆、目标、实体和决策关系，利用节点循环状态、时间间隔和邻域表示进行排序。查询、候选、焦点与评分时间只参与本次评分，不把后续标签提前写入图。近期、文本、目标和实体召回生成候选，集合组装再补齐依赖、修订和必要来源。

## 安装与训练

```text
uv sync --extra learning
uv run aurora train rhythm train-rhythm.jsonl valid-rhythm.jsonl models/rhythm.pt
uv run aurora train memory train-memory.jsonl valid-memory.jsonl models/memory.pt
```

输入文件需要自行准备有效标注，命令不从唤醒记录或曝光量自动推断正确效用。两种命令都支持 `--epochs`、`--hidden-size`、`--learning-rate` 和 `--seed`。训练在 CPU 工作线程执行；报告输出为 JSON，包含模型固定资源、原始数据资源、实际样本摘要、训练参数和独立验证指标。现有输出文件不会被覆盖。

输入 JSONL 在解析前固定为内容资源，训练始终使用该版本的字节。权重、输入来源和报告相互对应，导出文件与已发布模型使用同一份正文。路径删除之后仍可按 `weights_ref` 读取归档；更换权重不会改写旧运行事实。

## 节律数据格式

每行是一段连续经历：`schema_version = 2`、非空 `episode_id` 和非空 `examples`。同一经历只属于一个 Bot，观察时间与游标按顺序递增；不同经历之间重置循环状态。

每个样本包含：

| 字段 | 内容 |
| --- | --- |
| `observation` | 当时的 `bot_id`、带时区 `observed_at`、全局 `cursor`、`pending_events`、`elapsed_seconds`；可附目标、待核对动作、失败和计时特征 |
| `think_value`、`wait_value` | 在同一评价尺度下，立即推理与继续等待的效用 |
| `next_check_seconds` | 有限正数的下一次检查监督值 |
| `outcome_cursor` | 严格晚于观察的结果获知游标 |
| `outcome_at` | 不早于观察、带时区的结果获知时间 |

`aurorabot.rhythm.dataset` 提供 `RhythmExample`、`RhythmEpisode`、`write_episodes`、`read_episodes` 和 `validate_partition`。没有结果时间或游标的输入不能自动补成有效样本。标签可以来自独立任务评估、受控回放或标注，但要记录该效用何时真正可知。

训练与验证不能共享经历 ID，全部训练结果的获知时间必须早于任一验证观察；同一 Bot 的验证游标还必须越过它的全部训练结果。仅仅保证训练观察早于验证观察不够，因为训练标签可能来自更晚的结果。

## 记忆数据格式

记忆 JSONL 独立使用 `schema_version = 1`，每行包含 `episode_id`、`bot_id` 和 `examples`。每个样本包含完整的 `request`、逐候选 `utilities`、`outcome_cursor` 和 `outcome_at`。

`request` 保存当时的查询、焦点目标、世界游标、观察时间、候选内容和有序图交互。候选的发生时间、获知时间与游标不得超过本次读取边界；后续“采用”“成功”或反馈不能成为本次评分输入。每个候选需要有限效用标签，训练集至少有一组效用不同的候选。

`aurorabot.memory_model.dataset` 提供类型化读取和导出。监督结果必须晚于推荐游标，全部训练结果先于验证查询获知；同一 Bot 的验证查询不能复用训练结果之前的世界前缀。验证保留完整经历边界，不随机拆散相邻事件。

## 从实际运行收集输入

`aurora:rhythm/query/observations` 返回实际观察、判断、策略版本与有效参数，供后续标注。`aurora:memory/query/exposures` 区分候选、推荐、必要证据、实际载入和消息历史来源；`aurora:memory/query/training_input` 按某次模型请求的原始时间、游标和范围重建完整排序输入，要求指纹与实际审计一致。

Bot 可通过 `aurora:memory/command/feedback` 报告一项记忆是否帮助某个目标，并引用之后获得的证据。反馈是自评 `reported`，不自动成为正确标签；修订显式指向被替代的判断。原始事实和反馈都保留，训练输入不能混入后续更正。

## 启用模型与恢复

在 `rhythm.toml` 中选择 `policy = "aurora:rhythm/model/gru"`，在 `memory_model.toml` 中选择 `policy = "aurora:memory/model/tgn"`。分别设置导出文件的 `weights`，或设置训练报告给出的 `资源名@完整SHA256` 为 `weights_ref`。文件和固定引用只能选一项；正式启动会归档路径字节并校验实际加载版本，缺失或损坏不会静默切换到另一模型。

GRU 的消费位置、下一次检查时间和隐状态进入节律日志；版本或有效参数改变时清理不兼容状态。TGN 在线更新图投影，按配置间隔及关闭时保存检查点；启动恢复后仍验证完整查询前缀。原始经历与可读记忆独立于向量状态，投影失效不会删除事实。

## 如何判断是否有帮助

节律报告包括正确率、Brier 误差、效用遗憾和检查时长误差；记忆报告包括首位准确率、效用遗憾、NDCG 和正收益召回率。报告同时评估规则基线。受控测试证明梯度、历史依赖和导出重载，并在同一自主目标与重启场景中覆盖规则/GRU 与规则/TGN 的四种组合，不能推出开放任务上已取得收益。

实际任务评估应固定 LLM、任务、预算和数据可见边界，分别替换节律与记忆策略，再比较目标结果、推理消耗、延误、重复行动与恢复质量。记忆曝光是展示机会，不等于帮助；“更频繁唤醒”也不等于推进目标。两个模型初期分别训练，在线图状态更新不等于在线参数训练。

当前经历索引和图投影会随保留历史增长，输出和页面有界不保证候选计算恒定。自动摘要、在线参数优化和长期真实任务收益需要独立工作与证据，不由模型类名或测试通过推断。
